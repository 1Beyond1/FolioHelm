# ADR-0001：双证据 Journal 与远端指纹公证

状态：Accepted

日期：2026-08-09

## 背景

FolioHelm 需要在订单争议、网络超时、崩溃恢复和 Unknown 状态中保留可核对证据。用户要求证据同时保存在用户侧和项目侧，并且本地记录必须防篡改。

完整交易日志包含账户、Symbol、金额、数量、订单 ID 和时间线。如果项目服务器直接集中保存完整日志，会把 FolioHelm 从本地优先客户端变成金融数据托管方，显著扩大隐私、泄露、合规和运营责任。

## 决定

采用“本地完整证据 + 远端不可逆指纹”的双证据结构。

### 用户本机

- SQLCipher 保存完整、版本化的订单证据事件。
- 每个事件使用 SHA-256 形成前向 Hash Chain。
- 每个链条事件由当前设备 Ed25519 私钥签名。
- 私钥只保存在 Windows Credential Manager，不进入数据库、前端、日志或导出包。
- 订单写操作的 Journal 与状态更新在同一个 `synchronous=FULL` 数据库事务中完成。
- 用户可导出只读证据包；导出包包含事件、Hash、设备公钥、签名和远端回执，但不包含 Token 或 App Secret。

### FolioHelm 指纹公证端

- 只接收版本号、设备公钥、链序号、链头 Hash、客户端时间、应用版本和设备签名。
- 不接收账户号、账户 Hash、姓名、Symbol、方向、数量、价格、Broker Order ID、策略、持仓、余额或事件正文。
- 验证设备签名后保存 Commitment，并返回带服务端签名的 Receipt。
- Receipt 同时存回本地 Journal。发生争议时，重新计算本地链并与服务端 Commitment 对照。
- 公证服务不可用不能自动放行危险动作，也不能使已发送订单自动重试。离线 Commitment 可以排队，回执明确区分 `event_occurred_at` 与 `notarized_at`。

## 防篡改性质

该方案能发现：

- 修改历史事件正文。
- 删除链中间事件。
- 重排事件。
- 用其他设备密钥伪造原设备事件。
- 本地链被截断但远端仍保留更高序号 Checkpoint。

该方案不能单独证明：

- 事件正文一定真实反映了 Broker 行为。
- 设备在记录事件前没有被完全攻陷。
- 离线事件声明的本地时间准确。
- Schwab 行情或订单系统没有错误。

因此 Broker Order ID、Schwab 官方订单记录和 Broker Request ID 仍然是对账的重要外部证据。FolioHelm Journal 是可验证的辅助时间线，不宣传为绝对事实来源。

## 公证频率

- `dispatch_started`、Broker 明确响应、Unknown、Cancel / Replace 发送与最终状态：尽快提交 Checkpoint。
- 其他事件：最多每 100 条或每 5 分钟批量提交一次链头。
- App 正常退出、锁定和升级前提交一次最终 Checkpoint。
- 网络不可用时本地继续 Hash Chain；恢复后只上传最新链头及必要的连续 Checkpoint，不上传事件正文。

## 隐私与生命周期

- 公证端使用设备公钥作为伪名标识，不要求 Schwab 登录或 FolioHelm 云账户。
- 公钥和精确时间仍可能构成可关联数据，因此上线前必须确定隐私政策、保留期限、删除流程和司法辖区。
- 当前开发只实现本地 Journal、Commitment 数据结构和 `NotarySink` 接口，不部署远端服务，不进行网络上传。
- 公证端作为独立开源组件，允许用户自托管；官方端是否运营需要后续明确决定。

## 被否决方案

### 项目服务器保存完整日志

否决原因：泄露后直接暴露金融活动，扩大项目责任，不符合最小数据原则。

### 只保存本地普通日志文件

否决原因：用户或恶意软件可以修改、删除或重排，无法可靠说明完整性。

### 只保存本地 Hash Chain，不做远端 Checkpoint

否决原因：持有设备私钥和数据库的人可以重建整条历史，且无法发现尾部截断。

### 把每个订单公开写入公共区块链或 Transparency Log

否决原因：永久公开的时间、频率和可关联 Hash 仍可能泄露行为模式，删除困难，且没有必要。
